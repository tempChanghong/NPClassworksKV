# NPEP N2 通知契约草案

状态：历史讨论稿。2026-09-24 已形成未部署的实现候选，最终接口、边界、限制和隔离验证方式以 [NPEP-N2-NOTIFICATIONS.md](NPEP-N2-NOTIFICATIONS.md) 与 notifications.schema.json 为准；本稿保留设计背景，示例不作为最终 wire 契约。
范围：NPClassworks 的真实通知进入 NPEduTools 自定义置顶窗口；暂不接 ClassIsland。
设备端采用纯色背景、大字号白字、Swiss 风格，必须手动关闭。

## 1. 已核实的现状

- `prisma/schema.prisma`：发布类型为 `ASSIGNMENT`、`NOTICE`；状态为
  `DRAFT`、`PUBLISHED`、`WITHDRAWN`。N2 只读取 `NOTICE`。
- 通知级别为 `MINOR` 次要、`NORMAL` 普通、`IMPORTANT` 重要、`URGENT` 紧急。
  不新增或重新解释等级。设备颜色对应绿、蓝、黄、红；颜色之外仍显示中文等级。
- 通知具备 `publishAt`、`expiresAt`、`revision`、目标教学班与作者等信息。
- `domain/publication.js` 在写入边界规范化 `contentJson.popupEnabled`：普通、重要、
  紧急强制 true；次要仅显式 true 时启用。这是现有网页大屏策略。
- `POST /api/v2/classroom-screens/notification-deliveries` 使用网页大屏凭据。
  `NotificationScreenDelivery` 按 publicationId + screenBindingId 唯一，记录当前版本
  receivedAt/displayedAt/acknowledgedAt。旧版本被新版本替代，不能作为 N2 多版本事件账本。
- 现有回执归一化将 acknowledged 推导为 displayed；服务端按当前绑定、通知版本、
  PUBLISHED 状态及目标核验，旧版本或不匹配项可能跳过，响应只给 count。
  N2 需要逐项结果，不能照搬 count 判定全部成功。
- `domain/npep/wire.js` 与 N1 schema 只允许 `device.status`。
  `services/npepService.js` 当前 registration 和 approval 返回的是模块级能力常量，
  并非每个设备持久化的授权集合。不能直接向该常量追加通知能力。
- N1 已有实例/部署代际、绑定 revision、凭据失效、事务内再次校验和生命周期撤销。
  N2 必须沿用这些约束，不把网页 screen token 交给 NPEduTools。

## 2. 连接即接收：用户已确定的授权边界

本节覆盖初稿的“独立通知授权、强制重新配对”建议。N2 通知接收属于已连接设备的
默认功能，不增加通知申请、管理员二次审批或重新配对步骤。现有有效凭据可以在
升级客户端后使用 N2 接口；新连接仍须完成原有设备配对与绑定，不允许匿名读取。

每次拉取/回执仍检查凭据、实例与部署代际、当前绑定和教学班范围。连接不赋予修改
通知、代教师确认或学校管理权限。撤销、停用、解绑、凭据过期仍使通知访问失效。
不为本需求新增每设备通知 grantedCapabilities、审批记录或强制凭据轮换。

候选 wire 版本 `0.2`：N1 `0.1` 请求与响应保持原样，不把新字段塞进旧严格 schema。
设备升级后可继续使用原有效凭据，通过支持 N2 的接口读取通知；不要求旧版本客户端
理解或显示通知。supportedCapabilities 如需扩展只作协议功能发现，不作为新的审批流程。
不能直接改 N1 全局能力常量而破坏旧配对摘要、响应校验或客户端兼容性。
新服务未支持 N2 时，客户端明确提示通知暂不可用，保留原状态上报。

## 3. 最小业务接口

沿用 `/api/v2/npep`、Bearer 设备凭据、请求 ID、无缓存和统一错误信封。
以下是候选接口，不是现有可调用路径。

### GET /device/notifications

使用原有效设备凭据。设备不提交 schoolId/classId，服务器从当前授权绑定解析
行政班及允许关联的教学班，沿用现有目标解析规则。不得读取草稿、未来发布、撤回、
过期或不再属于当前绑定范围的通知。时间判断以服务器时间为准。

单条最小投影：publicationId、revision、title、纯文本 content、priority、
publishAt、expiresAt、经过裁剪的发布者显示名/班级显示名、服务端归一化后的 popupEnabled。
popupEnabled 投影自现有 contentJson.popupEnabled，并沿用现有等级规范化规则；
不新增独立桌面开关，不整包下发原始 contentJson、教师登录信息、回执明细或其他班级成员信息。
响应附 serverTime 和下一次轮询建议；正文按纯文本渲染，不执行 HTML、脚本或任意链接。

### 传输方式比较与第一阶段建议

| 方式 | 好处 | 需要承担的实现与运行成本 |
| --- | --- | --- |
| 定时 HTTP 拉取 | 复用已有 HTTPS/鉴权，断线恢复直观；适合先完成真实投递 | 延迟取决于轮询间隔；需要退避、随机抖动、限流，可用 ETag 减少正文传输 |
| HTTP 长轮询 | 有变化及时返回，不必频繁空轮询 | 服务端维护等待请求；超时、撤销、到期唤醒及网关连接配置需处理 |
| SSE | 单向通知变化推送，贴合服务端通知客户端 | 增加长连接管理、设备鉴权、代理超时和恢复机制；回执仍经 HTTP |
| Socket.IO | 可利用项目已有发布变更事件源，双向通信 | 现有网页 Socket 不能直接视作 NPEP 设备授权通道；需独立鉴权、订阅范围、撤销与重连处理 |

建议先采用 HTTP 快照拉取打通最小闭环；若优先追求及时性，可选“设备鉴权的 SSE
只发变更提示 + HTTP 拉取正文”，同一个拉取接口继续作为重连/低频补偿路径。
传输选择待双方定稿，不在本草案中提前实现 Socket 或持久化事件总线。
任何推送都不替代拉取时的实时授权核验，不通过状态广播附带任意通知正文。

快照复用现有通知查询规则，包含当前仍有效的目标通知；用 publicationId + revision
作为设备范围内稳定版本键，避免为了取得正文就新建发布模型或投递分发器。
不能静默截取前 100 条：分页必须有一致性约束，完整快照成功前不得用缺项删除本地内容；
分页失败保留原缓存、标记未完成并重试。最终需要定义快照版本/分页策略及更新时间竞争处理。
若采用 ETag，绑定范围、可见通知版本及定时生效/到期变化都必须使其失效。

对本阶段只保证“同步当前有效通知”，不承诺重放离线期间已发布又撤回/过期的每个事件。
若后续需要完整事件回放，再引入持久化事件游标和 UPSERT/INVALIDATE 日志；不将其作为
本次默认接收的前置工程。恢复网络立即核对；轮询遵守退避、抖动与 Retry-After。
重复响应不重复弹出同一版本。popupEnabled=false 仍可接收并保存，但不自动弹窗。

### POST /device/notification-receipts

使用同一有效设备凭据，不新增回执授权步骤。批量上限建议 100，逐项返回结果。候选请求：

```json
{
  "requestId": "UUID",
  "events": [
    {
      "eventId": "UUID",
      "publicationId": "publication-id",
      "revision": 3,
      "stage": "RECEIVED",
      "occurredAt": "2026-09-24T08:00:00Z"
    }
  ]
}
```

eventId 在本地落盘后重试保持不变。服务端按设备 + eventId 幂等：同 ID 同内容重复接受，
同 ID 不同内容返回冲突；唯一投递记录按 deviceId + publicationId + revision 隔离。
服务端保存 receivedAt 等接收时间，occurredAt 仅作客户端声明，不能作为权限或排序依据。
允许批次部分成功，返回 ACCEPTED/DUPLICATE/REJECTED 与稳定原因；客户端只清除已确认项。
临时错误重试，失去授权停止并隔离队列，不把旧队列换账号/绑定重放。

已接受的 RECEIVED 记录可作为该设备曾接收此版本的历史证据。撤回/到期后的迟到回执
只有在仍有效的设备身份/绑定下、且能核验历史接收范围时才接受；完全离线后才上传全部
阶段且无法证明历史范围的情况，返回明确逐项拒绝原因，不能伪造成功。是否补足离线历史
接收凭据待定，不为快照接口强制引入服务端投递分发器。旧 revision 不更新新版状态，
不把撤回恢复为有效。
实际写入前在事务内重新核验设备身份和绑定；遵守 N1 锁顺序，避免与撤销并发交错。

## 4. 三种事件的精确定义

| stage | 产生条件 | 明确不表示 |
| --- | --- | --- |
| RECEIVED | 设备已校验并持久化完整该版本通知 | 窗口已显示、人员已阅读 |
| DISPLAYED | 窗口创建及内容渲染成功，实际进入显示状态 | 用户已看到/理解、手动关闭 |
| DISMISSED | 用户明确点击关闭该通知 | 教师确认、学生个人已读 |

入待显示队列、窗口创建失败不能记 DISPLAYED。锁屏/会话不可交互时延后显示并保留 RECEIVED。
进程退出、系统关机、崩溃、远程撤回、超时或窗口被系统销毁都不能记 DISMISSED。
回执乱序可落盘为独立事实，但不得凭 DISMISSED 伪造前两阶段的客户端发生时间。
本地写入阶段事件后再上传；重启恢复未关闭通知，已关闭同版本不再弹出。
新版通知有新投递键，允许再次提示；不能将旧版本的关闭归给新版本。

NPClassworks 管理界面需区分“网页大屏回执”和“NPEduTools 回执”。N2 数据单独存储，
不得直接覆盖 NotificationScreenDelivery，也不将 N2 手动关闭等同旧 acknowledgedAt。

## 5. 展示与生命周期规则

- 置顶窗口的颜色映射按用户要求；黄色背景上的白字需选择足够深的黄色保证可读性，
  不自行改为黑字。正文可滚动，长标题/长正文不截断，关闭入口可键盘访问。
- 多条通知建议排队，紧急优先，同级按发布时间稳定排序；被抢占不是手动关闭。
  不借由自动超时移除窗口，不将优先级当作系统命令权限。
- 已撤回/过期/失去授权的正文不能一直保留并被误认为仍有效。建议立即清除正文，
  窗口保留“已撤回/已过期/授权失效”的状态页，由用户关闭；此关闭不伪造有效通知阅读确认。
- 断网期间已显示窗口保留离线状态；到达服务器时间推算的到期点转过期状态，
  重连后先核对有效性。敏感正文不写诊断日志，缓存与回执按实例/代际/设备/绑定隔离。
- 暂不新增提示音规则，沿用还是独立配置应另行明确，不从窗口颜色推导音效。

## 6. 契约待对齐项

1. 已确定：网页和桌面复用同一个 popupEnabled。普通/重要/紧急按现有规则为 true；
   次要为 false 时接收但不自动弹窗，不伪造 DISPLAYED 或 DISMISSED。
   四级颜色只规定“显示时的样式”，不意味着四级全部强制弹窗。
   非弹窗通知若没有用户可访问的通知中心，则保持 RECEIVED，不假定已展示。
2. 通知编辑时正在显示的旧版：建议原窗口更新为新版并提示更正，关闭仅归当前渲染版本；
   必须防止按钮点击与版本替换竞争。纯文案变化与其他revision变化是否全部重弹需定稿。
3. 断网恢复回放范围：建议当前仍有效且未关闭的已授权通知；过期历史只保留回执，
   不重弹。新配对是否补当前全部有效通知需显式确认。
4. 撤回/到期状态页、快照分页与历史回执保留时间，是实现前需要确认的协议细节。

## 7. 必须覆盖的验证

- 原有效凭据可用于升级客户端的 N2 通知接口，无需重新配对；旧 N1 请求/响应保持兼容。
- 匿名、过期、已撤销或绑定不匹配的凭据被拒绝，默认接收不演变为全校通知访问。
- 原有配对审批权限不变；停用、解绑及代际改变与拉取/回执并发时仍拒绝越权。
- 定时未到、已撤回、过期、跨学校/跨班通知不泄漏；走班目标按现有规则匹配。
- 四等级原样传输，未知枚举拒绝并报告，不能将 MINOR 自动升级 NORMAL。
- 接收后崩溃、显示失败、显示后断网手动关闭、重启补传、重复/乱序/冲突eventId。
- 编辑后旧回执不确认新版；撤回/到期/权限撤销后的窗口与正文处理。
- 超一页快照、分页失败、定时发布/到期导致缓存失效，以及并发修改不造成静默漏项或重复弹窗。
- 次要popupEnabled=false在网页和桌面均不自动弹窗，只接收；其他等级继续按现有规则弹窗。
- 同一班网页大屏与NPEduTools同时运行，回执互不覆盖，明确重复提示策略。

后续步骤：双方先确认传输、快照与三阶段回执语义，再冻结0.2 schema及契约测试；
此草案不构成生产启用N1/N2的指令，不修改现有部署代理或发布门槛。
