# 自动部署的前后端版本配对

部署代理 `deploy/agent/server.js` 和 GitHub Actions 签名请求格式保持原样，不需要朋友更新或重启代理。

后端 `upgrade.sh` 获得部署锁后，获取两边 Git 引用并一次性解析为完整提交 SHA。它从这两个提交读取 `deploy/compatibility.json`，通过校验后才备份、切换到固定 SHA 并构建。执行期间 `main` 再次变化不会改变本次计划。

## 配套变更的规则

两个仓库均声明 `schemaVersion: 1`、各自 `component` 和相同的 `compatibilityEpoch`（当前为 `1`）。

- 普通兼容修改保持 epoch 不变。
- 前后端必须一起切换的不兼容变更，两边同时提升 epoch。任何一边先推送都会因 epoch 不匹配停止升级，当前应用继续运行；第二边到齐后重新触发即可。
- 前端依赖某次已经提交的后端兼容新增功能时，可在前端声明 `requiresPeerCommit` 为所需后端的完整 SHA；反向依赖同理。对端所选版本必须包含该提交，否则停止升级。删除依赖前需确认旧版本已不再支持。

这些声明由维护者随配套变更更新；它们不能自动推断任意两次提交的业务兼容性，也不能替代测试。现有代理没有向脚本传递触发请求里的 commit，因此计划固定的是获得部署锁后读取的两边引用，不能声称它一定等于本次 GitHub Action 的触发 SHA。

## 版本记录

后端 `deploy/runtime/release-*.json` 留存每次解析成功的计划，包括完整 SHA 和兼容性声明。只有构建、启动及健康检查成功后，才更新 `deployed-release.json`；回滚同时恢复上一份版本记录。版本文件不含生产密钥。

首次将新脚本部署到服务器的升级仍由服务器上的旧脚本执行。从之后的升级调用起，新校验才生效。此过程沿用现有自动部署，不需要修改代理程序、环境变量或数据库。

## 本地验证

后端 `node --test tests/releasePlan.test.js` 使用临时 Git 仓库验证引用移动、不匹配声明、缺失声明和对端依赖提交。它不连接生产服务器，也不触发部署。
